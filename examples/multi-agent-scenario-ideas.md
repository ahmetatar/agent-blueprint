# GrowOps — Autonomous Vertical-Farm Operations Brain

> A single, end-to-end demo that exercises **every** ABP capability on one
> believable story: an autonomous controller that runs a commercial
> vertical-farm grow room, on a schedule, talking to **ESP32** sensor/actuator
> nodes, and deployed to **Azure Container Apps**.

Status: concept for evaluation. Nothing here is implemented yet. This document
replaces the earlier eight-example "ladder" — the goal changed from *a tutorial
pile* to *one flagship demo that proves the whole product on a real workload*.

---

## Why this domain

- **Enterprise, but not slideware.** Controlled-environment agriculture (CEA) /
  vertical farming is a real, capital-intensive industry with real telemetry,
  real safety constraints, and real cost ceilings — not another support bot.
- **Genuinely IoT.** ESP32 is the de-facto microcontroller for grow-room
  sensing (soil moisture, air temp/RH, CO₂, lux, leaf wetness) and actuation
  (pumps, fans, vents, grow-lights, nutrient dosers). The agent's job only
  exists *because* there's hardware in the loop.
- **Autonomous + schedulable.** The interesting unit of work is an unattended
  **grow cycle** that fires on a clock (hourly) and on threshold events — no
  human typing prompts. That is exactly the workload ABP's runtime guarantees
  (approvals, budgets, contracts) were built for.
- **Forces every feature to earn its place.** A door that won't unlock itself is
  cute; a grow-light that costs money and a nutrient dose that can kill a crop
  give *approvals*, *budgets*, and *escalation* visceral, non-toy stakes.

## The autonomous architecture (and its honest boundaries)

```
                ┌──────────────────────── Azure ────────────────────────┐
                │                                                        │
 ESP32 sensors ─┼─MQTT/HTTP─▶ Sensor Gateway ◀─ read_sensors (api,       │
  (soil/air/CO₂/│                 (HTTP)         api_key auth)           │
   lux/wetness) │                                   ▲                    │
                │                                   │                    │
   Container Apps JOB (cron, hourly) ──POST /invoke─┴──▶ GrowOps agent   │
        + threshold webhook ──────────POST /invoke──────▶ (Container App,│
                │                                          scale-to-zero)│
 ESP32 actuators┼◀─HTTP poll─ Actuator Gateway ◀─ set_actuator (api,     │
  (pump/fan/vent│                 (HTTP)           bearer, approval-gated)│
   /light/doser)│                                                        │
                │   grow_report.md ─▶ Blob      OTel ─▶ Azure Monitor    │
 agronomist ◀───┼── Slack handoff ◀── escalation / approval circuit      │
                └────────────────────────────────────────────────────────┘
```

**What ABP generates:** the agent (FastAPI `/invoke` + `/health`), all graph
logic, the `api`/`function`/`retrieval` tool bindings, policy enforcement,
artifacts, OTel export, and the Azure deploy (`abp deploy --platform azure`:
ACR build + Container Apps, `min_replicas: 0` so it sleeps between cycles).

**What is demo scaffolding (NOT generated by ABP), and we'll say so:**
1. **The scheduler.** ABP does not emit cron/queue triggers (see `docs/deploy.md`
   — "Non-HTTP triggers are not generated"). A **Container Apps Job** with a
   cron schedule (or a Logic App timer) calls `POST /invoke`. Documented pattern.
2. **The two gateways + ESP32 firmware.** The agent talks to a Sensor Gateway and
   an Actuator Gateway over plain HTTP `api` tools. Those gateways (and the ESP32
   sketch that feeds/polls them) are tiny companion services shipped *alongside*
   the example, so the demo is runnable end-to-end — but they are outside ABP's
   surface. In `abp test` they're deterministic tool stubs (no hardware needed).
3. **Cross-cycle memory.** `thread_id = bed/zone id` → each grow bed is its own
   LangGraph thread, so the agent "remembers last cycle." Behind a scaling
   Container App that needs a shared backend (`memory.backend: postgres`), not
   `in_memory` — called out honestly per `docs/deploy.md`.

**The human circuit-breaker (the design crux).** In headless autonomous mode an
approval-gated actuator (grow-light, nutrient dose) can't pop a console prompt.
So high-stakes actions are *approval-gated AND* route to a **Slack handoff** for
a human yes; only low-stakes actions (open a vent, nudge a fan) auto-commit. The
exact "approval-in-headless" mechanics are the one thing to validate first in
step 3 — it's the most interesting runtime question this demo asks.

## The agent graph

```
START ─▶ ingest            (function node: parse ESP32 telemetry → typed state)
ingest ─▶ sense            (parallel: [irrigation_analyst, climate_analyst,
                                        pest_analyst]  join: synthesize)
synthesize (agent)         emits GrowAssessment {status, risk_level, confidence,
                           recommended_actions}  ← output contract
synthesize ─▶ ⚡ escalation: confidence < 0.7  → ask_agronomist (handoff/slack)
           ─▶ default                          → plan
plan = supervisor(grow_ops)  workers: [irrigation_actuator, climate_actuator,
                                        nutrient_dosing]  max_iterations: 6
                             on_finish: safety_gate
                             (dynamic delegation: only run the specialists the
                              situation needs — efficiency is the point)
safety_gate = subgraph(safety_flow: propose → critique → finalize)
                             REUSED via input_map/output_map (actuation plan +
                             nutrient plan run through the same review flow)
safety_gate ─▶ risk == 'high' → ask_agronomist
            ─▶ default         → commit
commit (agent)               calls set_actuator (api, bearer); set_grow_light &
                             dose_nutrients are approval-gated → Slack yes
commit ─▶ report             (agent → grow_report.md artifact, bound to contract)
report ─▶ END
ask_agronomist ─▶ END
```

Node types used: `function`, `parallel`, `agent`, `supervisor`, `subgraph`,
`handoff` — the full set. Routing uses conditional edges + escalation.

## Offline-first (the example is a living test)

Every tool has a deterministic stub and every LLM call a mock fixture, so
`abp test examples/growops/growops.yml` passes **with no API key and no
hardware**. The ESP32 gateways are never contacted in test/CI. The grow room
runs in software before it ever runs in a greenhouse.

Proposed layout (one example = one directory — it carries datasets + a corpus):

```
examples/growops/
  growops.yml                 # the blueprint
  tools/impl.py               # function-tool + retriever impls
  corpus/                     # agronomy / plant-disease markdown for RAG
  datasets/                   # eval datasets (status classification, policy)
  companion/                  # NON-ABP demo scaffolding:
    sensor_gateway.py         #   fake Sensor Gateway (FastAPI)
    actuator_gateway.py       #   fake Actuator Gateway (FastAPI)
    esp32/grow_node.ino       #   reference ESP32 sketch
  README.md                   # the end-to-end + Azure walkthrough
```

CI must extend the smoke step from `abp validate examples/basic-chatbot.yml`
(now deleted) to validate + lint + `abp test` this example. **Action item:**

## Build plan (step 3, when approved)

1. **Validate the crux first:** prove the approval-in-headless circuit
   (approval-gated actuator → Slack handoff → confirm on a follow-up `/invoke`)
   on a minimal 3-node blueprint before building the full graph.
2. Grow the blueprint outward, `abp validate` + `abp lint` green at each step,
   then `abp test` scenarios (routine → escalation → approval → budget-blown).
3. Add evals + datasets + a committed gate baseline; wire the traces flywheel.
4. Ship the companion gateways + ESP32 sketch + the Azure walkthrough README.
5. `abp deploy --platform azure`; point a Container Apps Job (cron) at `/invoke`;
   record the demo.

## Open questions for evaluation

1. **Scope of v1:** ship the full matrix in one PR, or land a runnable core
   (sense → plan → commit → report + harness) first, then layer evals/gate/OTel?
2. **Memory backend in the demo:** `postgres` (honest for a scaling Container
   App) or `sqlite` (simpler, single-replica, pairs with `abp package`)? Could
   show both: `sqlite` for the local CLI, `postgres` for the Azure deploy.
3. **MCP:** keep it staged-and-documented like the rest of the repo, or leave
   MCP out of this demo entirely until generation exists?
4. **Crop:** leafy greens (fast cycle, forgiving — good for a demo) vs. a
   higher-stakes crop (more dramatic approval/escalation stakes)?
